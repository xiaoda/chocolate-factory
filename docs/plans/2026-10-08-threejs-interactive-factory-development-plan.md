# 巧克力工艺 three.js 互动科普开发方案

> 执行说明：后续实施时使用 `executing-plans` 技能按任务推进，每个阶段完成后检查结果；本文件仅为开发方案，不代表已经实现、测试或验收。当前只保存方案，不安装依赖、不启动服务、不自动提交 Git。

> 实施状态更新（2026-10-08）：用户随后授权开始，已执行第一批任务 1–3，交付涂层机可旋转的静态造型样板及本地页面集成。完整工序动画尚未实现；当前停在静态造型评审检查点。实际验证见 `web/three/验收记录.md`。上面的“只保存方案”是方案创建时的范围，不是后续实施状态。

**目标：** 基于项目中的设备实拍与工艺资料，制作可旋转查看、可播放工序、可观察进出料和物料变化的网页 3D 科普内容。

**架构：** 保留现有 Python 静态网页生成器和九条工艺路线，以独立的 three.js 模块渐进增强页面。设备全部优先使用代码生成几何体；工艺数据、设备结构、动画时间轴和网页交互分离，通过共享设备库逐步扩展。

**技术栈：** Python 标准库、TypeScript、three.js、Vite、Vitest、原生 HTML/CSS、Chrome DevTools MCP；版本在实施开始时核对兼容性并锁定。

**日期：** 2026-10-08。

**已确认约束：** 面向网页互动科普；先不用 Blender。首期不依赖外部 3D 建模软件、付费图片转 3D 服务或在线模型生成接口。

## 1. 项目现状与设计边界

### 1.1 可复用资产

截至本次调研，项目已有：

- `photos/`：34 张原始参观照片；现有分析识别出至少 14 类设备或装置。
- `web/content.py`：9 条工艺路线、49 个讲解步骤，包含输入、动作、输出、照片、展牌和资料来源。
- `web/build.py`：生成 1 个总览和 9 个工艺单页。
- `web/dist/assets/style.css`、`app.js`：现有视觉样式和图片查看等交互。
- `web/test_site.py`：内容、页面结构、本地引用和图片信息检查。
- `web/serve.py`、`start_preview.py`：仅监听 `127.0.0.1` 的本地只读预览及隐藏启动器。

照片适合提取设备轮廓和主要部件，不是完整环拍数据，也没有足够的尺寸、背面和内部机构资料。九条路线是按资料整理的典型工艺，不代表照片中的设备历史上配套运行。

### 1.2 产品定位

定位为“基于实拍的设备与工艺互动图解”，而非精密复刻、工业数字孪生或生产操作规程。

优先级依次为：

1. 看懂什么进去、发生什么、什么出来。
2. 看懂设备的关键工作部件与物料路径。
3. 能将简化模型与实拍设备对应起来。
4. 动画流畅、交互顺手、风格统一。
5. 在必要位置逐步补充造型细节。

### 1.3 首期明确不做

- 不使用 Blender，不引入必须由外部建模软件维护的资产链。
- 不自动上传照片，不购买或调用图片转 3D 服务。
- 不做真实流体、颗粒碰撞、热传导、结晶或产能仿真。
- 不从照片推算精确尺寸、真实转速、加工温度和停留时间。
- 不做第一人称工厂漫游、VR、多用户协作、账户系统或数据库。
- 不把全部设备硬连成一条生产线，不给 29、40 等待辨识照片强行命名。
- 不要求第一版同时覆盖所有设备、所有工艺或全部内部机构。
- 不以动画替代现有图文正文，不修改照片原件。

## 2. 总体实现路线与关键决策

| 决策 | 采用方案 | 原因与代价 |
|---|---|---|
| 模型制作 | three.js 程序化几何体与参数化组件 | 部件和旋转中心可控，不依赖 Blender；复杂曲面需要额外代码与视觉迭代 |
| 页面技术 | 原有静态站点＋独立 TypeScript 模块 | 避免重写为 React；需要明确 Python 与前端模块的构建顺序 |
| 动画机制 | 统一时间轴＋按时间求值的状态函数 | 支持暂停、跳转、重播；比随意累加位置更需要前期结构设计 |
| 物理表达 | 可解释的视觉近似，不做物理引擎仿真 | 性能和教学节奏可控；必须标注时间、比例、运动为示意 |
| 工艺内容 | 复用 `content.py`，新增场景映射 | 减少文案不一致；需要为已接入步骤增加稳定 ID |
| 上线范围 | 先涂层机单场景，再设备库，再多路线 | 先验证样板质量；其他页面暂不提供空壳 3D 入口 |
| 运行方式 | 所有运行依赖本地打包，经 HTTP 提供 | 离线于互联网仍可使用；3D 不承诺支持直接双击 HTML |

以上作为当前架构决策记录；后续变更需记录原因、影响和回退方式，不为未来可能需要的功能提前增加服务或框架。

## 3. 用户体验设计

### 3.1 首期页面位置

在 `enrobed.html` 的流程速览后、详细步骤前增加独立的“看设备怎样工作”区域。原有照片、正文、来源、阅读导航和打印内容继续保留。

初始显示实拍图、简短说明与“加载 3D 演示”按钮。用户主动加载后才引入 three.js 和创建渲染器；默认暂停，避免突然运动、额外资源开销或影响阅读。

首期区域包含：

- 3D 画布：设备、物料、地面、输入输出方向及必要热点。
- 讲解栏：当前阶段、进入的物料、发生的变化、得到的物料。
- 操作栏：播放/暂停、重播、进度、上一步/下一步、复位视角。
- 视图切换：完整外观、工作部件示意、实拍对照。
- 证据提示：外观参考实拍；补充结构、冷却段和物料路径属于典型原理示意。

首期暂不加入倍速、配音、背景音乐、全屏、自由编辑生产线或复杂参数调节。需要时在样板验收后追加。

### 3.2 三种视图的语义

1. **完整外观：** 保留与照片一致的主要轮廓，不追求每个按钮和紧固件。
2. **工作部件示意：** 隐藏部分外壳或将部件适度分离，突出网带、淋涂头和回收区域；不能把自动剖切当成已还原内部机构。
3. **实拍对照：** 桌面可并排，手机可切换；照片 25 为设备、26 为展牌，可复用现有图片放大功能。

相机拖动只改变观察角度，不改变工艺时间；用户主动旋转后不自动抢回视角。阶段按钮可提供显式的“查看此部位”，第一版不强制自动运镜。

### 3.3 无障碍与移动端

- 所有控制使用真实按钮、范围输入等 HTML 元素，键盘可操作，焦点清楚。
- 输入输出和物料状态同时用文字、位置或图形区分，不只靠颜色。
- `prefers-reduced-motion` 开启时仍以静止画面起步，允许逐步查看，不自动运镜。
- 讲解状态只在阶段变化时播报，不每帧刷新屏幕阅读器提示。
- 手机限制旋转范围，画布外保留正常滚动区域，不接管整页触摸手势。
- 320 px 宽度下控制按钮可换行，页面不得横向溢出。
- 打印时隐藏画布与控制，保留静态图、输入输出说明和资料边界。

## 4. 首个样板：巧克力涂层机

### 4.1 选择依据

首期默认选择照片 25／26 对应的涂层机。它的机柜、网带、涂层头容易用代码建立，且能同时展示机械运动、两路输入和明显的物料变化，适合验证整个技术路线。

参考 `web/content.py` 的 `enrobed` 页面，不重新编造另一套工艺。第一版选择一种准备好的饼干芯体，不同时支持多个产品配方。

### 4.2 场景组成

| 场景对象 | 实现方式 | 证据边界 |
|---|---|---|
| 机柜、立柱、罩体 | 方体、倒角几何、挤出形状 | 比例依据照片估计，不标注真实尺寸 |
| 网带与驱动辊 | 辊筒＋重复横条或程序化纹理 | 运动方向用于教学，需明确不是历史配置测绘 |
| 料槽、淋涂头、管路 | 盒体、旋转曲面、管道 | 可见部分参照照片；隐藏连接按原理示意 |
| 巧克力幕 | 简单曲面或薄片＋流动效果 | 非真实流体，不宣称模拟真实黏度 |
| 饼干芯体 | 可复用的简化几何体 | 代表性产品，不声称照片中的原生产产品 |
| 产品外层 | 与芯体配合的独立外壳几何 | 随位置逐渐出现，避免仅换颜色导致看不懂包覆 |
| 接料与回流 | 简化接料盘和带方向标记的路径 | 典型回收原理；不伪造不可见的泵体结构 |
| 控量部位 | 风向线、轻微振动与涂层变化 | 明确控量不等于冷却凝固 |
| 冷却段 | 独立的抽象冷却区域或简化隧道 | 照片未明确拍到，持续标注“补充工序示意” |

第一版采用明确的涂层配置；若展示全包覆，应表现底涂，不能只淋上表面却声称底部已完成包覆。半涂、仅底涂等配置不在首期交互范围内。

### 4.3 75 秒讲解分镜初稿

时间为教学编排，不对应真实加工时间。下列时长可在样板评审后调整。

| 时间 | 阶段 | 画面与说明 | 对应现有内容 |
|---|---|---|---|
| 0–12 秒 | 认识输入 | 已制好的饼干与准备好的巧克力料分别出现；说明涂层机不制造饼干 | 芯体制备、涂层料准备 |
| 12–30 秒 | 经过涂层区 | 网带前进，展示淋涂及选定配置下的底涂，外层逐渐形成 | 排料、淋涂、底涂 |
| 30–44 秒 | 控量与回收 | 展示多余料离开产品、回收路径及适度吹风/振动 | 振动、吹风控量 |
| 44–63 秒 | 冷却定型 | 产品进入另一区域，标签从“未充分凝固”变为“已定型” | 冷却、包装中的冷却环节 |
| 63–75 秒 | 检查输出 | 停留在成品和输入对照，重述两路输入、关键动作和输出 | 成品与流程总结 |

默认播完停在成品阶段，不自动循环。真实物料在各区同时加工的连续生产概念，可用多个错开位置的产品表达，但被讲解的主产品必须易于追踪。

首期不建模真实包装机构；用文字说明下游检查包装。调温仅作为已完成的前置条件，不把调温动画塞进涂层机。

### 4.4 样板验收的三个问题

无需阅读长文，观看者应能回答：

1. 机器接收哪两类输入？
2. 淋涂、控量和冷却各自完成什么？
3. 为什么刚经过巧克力幕的产品不能立刻当作已凝固成品？

## 5. 程序化建模规范

### 5.1 视觉规则

- 延续项目的奶油纸色、深可可色、铜色点缀；设备主色参考照片。
- 使用低细节、圆润、略卡通的工业造型，避免完全写实，也避免过度玩具化而失去结构辨识度。
- 关键工作区域放大、留空，隐藏与教学无关的紧密零件。
- 金属采用适度粗糙度；首期不使用重反射、大型环境贴图和昂贵后处理。
- 不复刻锈迹、掉漆、展陈投影光效或背景栏杆。
- 文字主要使用 HTML 标签，不把大量中文烘焙到纹理里。

### 5.2 几何组件

优先复用：机柜、支腿、料斗、圆桶、辊筒、输送段、简单电机、弯管、控制面板和地台。

造型工具优先使用 three.js 自带几何体、`Shape`/`ExtrudeGeometry`、`LatheGeometry`、`TubeGeometry` 等。首期不引入 CSG；必要的开口优先通过分片、旋转曲面或有厚度的壳体直接构建。

所有设备返回有语义的部件引用，而不是依靠 `children[3]` 一类易失效的索引查找。

```text
enroberRoot
├─ cabinet
├─ conveyor
│  ├─ belt
│  └─ driveRollers
├─ coatingHead
├─ collectionTray
├─ blowerGuide
├─ ports
│  ├─ coreIn
│  ├─ chocolateIn
│  ├─ coatedOut
│  └─ returnFlow
└─ hotspots
```

### 5.3 坐标和轴心

- 统一采用 Y 轴向上，演示主物流沿 X 轴前进；坐标按约定的场景单位使用。
- 场景单位只为组合和视图一致，不表示已测量到真实米制尺寸。
- 旋转部件以 `Group` 建立局部轴心；移动部件保存初始变换。
- 进出料接口包含位置和方向，物料路径跟随设备布局，不在多个模块硬编码坐标。
- 每台设备记录外形参数、部件名、接口名、照片编号、已知结构和示意结构。
- 纯色圆柱旋转可能不可见，可增加少量中性标记帮助观察，并标注为演示辅助。

## 6. 数据与代码架构

### 6.1 数据流

```text
web/content.py                    web/scene_content.py
工艺正文、输入输出、照片、来源       设备映射、阶段时长、热点与示意边界
              \                    /
                 export_scene_data.py
                         ↓
            web/three/generated/enrobed.json
                         ↓
          TypeScript 数据校验与静态打包
                         ↓
        场景状态求值 → 设备/物料更新 → three.js 画面
                         ↓
                   HTML 讲解与控制
```

首期只导出涂层场景所需的数据。为 `enrobed` 的五个正文步骤增加稳定 `id`，不一次性重构其他八页。动画阶段用稳定步骤 ID 关联，不能将数组下标当长期接口。

正文的输入、动作、输出继续由 `content.py` 提供；动画专用短字幕可写在 `scene_content.py`，但必须声明对应正文步骤和来源。一个动画阶段可以关联多个正文步骤。

### 6.2 核心接口草案

以下是实施时应维持的最小契约，不要求第一天完成通用编辑器或完整图引擎。

```ts
import type { Group, Vector3 } from 'three';

export type EvidenceKind = 'photo' | 'reference' | 'schematic';

export interface Port {
  position: Vector3;
  direction: Vector3;
}

export interface MachineInstance {
  root: Group;
  ports: Record<string, Port>;
  setView(mode: 'exterior' | 'working'): void;
  applyState(state: SceneState): void;
  dispose(): void;
}

export interface Phase {
  id: string;
  start: number;
  end: number;
  stepIds: string[];
  title: string;
  evidence: EvidenceKind;
}

export interface SceneState {
  time: number;
  phaseId: string;
  phaseProgress: number;
  productPosition: number;
  coatingCoverage: number;
  coolingProgress: number;
}

export interface SceneController {
  play(): void;
  pause(): void;
  seek(seconds: number): void;
  restart(): void;
  resetView(): void;
  dispose(): void;
}
```

模型自身不读取 DOM，也不自行启动无限动画循环。一个场景只有一个主循环和一个控制器。

### 6.4 构建与原站点隔离

完整构建顺序固定为：

1. Python 校验并导出场景数据。
2. TypeScript 类型检查与 Vite 生产构建。
3. Python 使用 `--with-3d` 生成包含模块引用的页面。
4. 运行静态站点及新增数据测试。

Vite 只允许输出到 `web/dist/assets/three/`，不得把输出目录设成 `web/dist/`，不得清空现有页面、照片、`style.css` 或 `app.js`。配置相对资源路径，入口使用明确可引用的文件名（例如 `viewer.js`、`viewer.css`），内部块可带哈希；用构建测试确认实际产物，而非依赖命名猜测。

`python web/build.py` 保留原有纯图文构建能力；完整 3D 版本统一用 `python web/build_all.py`。明确请求 3D 构建时，缺少模块应失败退出，不静默输出缺失功能的页面。

`build_all.py` 的子进程必须检查退出码。Windows 使用无窗口启动方式，注意 `.cmd` 命令的实际启动链，不能只隐藏外层 Python 就假定 npm 子进程不会弹窗。

## 7. 动画机制

### 7.1 状态由时间决定

核心函数为 `evaluateEnrobed(time, sceneData)`：在相同数据、时间和固定种子下返回相同状态。时间以秒为单位，限制在 `[0, duration]`。

禁止将 `rotation += 常量`、`position += 常量` 作为工艺状态的唯一来源；否则帧率变化、暂停和跳转后容易不同步。机械转角、产品位置、涂层覆盖和冷却状态统一从场景时间计算。

进度条拖动后必须直接定位，而不是快速播放前面的动画。`seek()` 不隐式切换播放/暂停状态；到达结尾自动暂停；重播从 0 开始。

示例验收测试：

```ts
import { expect, it } from 'vitest';
import { evaluateEnrobed } from '../src/core/timeline';
import sceneData from '../generated/enrobed.json';

it('同一时间的状态不依赖之前的播放路径', () => {
  const expected = evaluateEnrobed(40, sceneData);
  evaluateEnrobed(70, sceneData);
  evaluateEnrobed(5, sceneData);
  expect(evaluateEnrobed(40, sceneData)).toEqual(expected);
});

it('越界时间被限制在场景有效范围内', () => {
  expect(evaluateEnrobed(-5, sceneData).time).toBe(0);
  expect(evaluateEnrobed(999, sceneData).time).toBe(sceneData.duration);
});
```

### 7.2 物料表达

- 输送采用路径参数与产品间距；重复产品优先共享几何和材质。
- 产品首次显示、消失和复用应安排在明确的进出料边界，不在观看区域突然闪现。
- 包覆状态按产品穿过涂层区的位置计算，而非所有产品同时换色。
- 流动效果使用程序化材质或少量几何，不依赖外部图片或实时流体模拟。
- 重复实例数量较多时使用 `InstancedMesh`；小规模先保持实现清晰，性能数据证明需要时再优化。
- 任何演示性粒子、风向线、透明路径都需与实际产品区分，不能误认为原料或真实管道。

### 7.3 生命周期

- 页面隐藏或画布离开可视区时暂停时间推进，不在恢复时补跳几十秒。
- 暂停时仍可通过相机交互触发必要重绘，不持续满速空转。
- `ResizeObserver` 处理容器尺寸变化，不只监听窗口尺寸。
- 销毁时移除事件、观察器、动画回调并释放自有 GPU 资源；共享几何和材质只释放一次。
- WebGL 初始化失败、上下文丢失、脚本加载失败时，保留图文回退和明确提示；首期允许显式重试，不做无限重试。

### 9.2 浏览器验证约定

- 优先发现 `chrome-devtools` 工具，先调用 `list_pages`。
- 自主测试调用 `new_page` 创建本任务页面，使用唯一 `isolatedContext`，记录返回 `pageId`。
- 所有操作显式使用已确认归属的 `pageId`；不接管其他任务标签。
- 通过 `take_snapshot` 检查结构、`take_screenshot` 检查视觉；截图只返回路径时必须实际查看图片。
- 桌面以 1440×1000 验证，移动尺寸至少覆盖 390×844 和 320×780。
- 查看控制台错误、资源请求失败和 JS/CSS 类型；只在看到页面后记录“已渲染”。
- 渠道连接、地址可访问、页面渲染分别记录；失败时保留具体错误，不把单一渠道失败说成浏览器整体不可用。
- 不上传公网，不监听 `0.0.0.0`；只停止本任务创建且不再需要的进程、关闭本任务创建的页面。

### 9.3 功能与内容门槛

- 原有十页、图片放大、来源链接、打印和阅读导航无回归。
- 只有已完成的场景显示可用入口，不展示无法使用的“即将支持”控制。
- 播放/暂停、重播、进度跳转、逐阶段查看、旋转、复位、实拍对照均有效。
- 同一时间的产品位置、包覆状态、冷却状态和字幕一致。
- 输入、动作、输出关系正确，动画没有把控量当冷却，也没有把前置调温塞进涂层机。
- 所有非实拍结构和工序有示意边界；不伪造配方参数和历史配置。
- 任意 3D 故障仍可阅读正文和照片；键盘与窄屏可完成主要操作。

### 9.4 性能目标与测量

以下为初始工程目标，需样板实测后调整，不代表已经达成：

- 明确记录的桌面设备以接近 60 FPS 为目标；后续选定的真实中端手机以稳定 30 FPS 为目标。
- 浏览器移动尺寸模拟只验证布局，不能替代真实手机 GPU 与温升测试。
- 首期单场景初步控制在 15 万三角面、150 次绘制调用以内；这是诊断预算，不是流畅保证。
- 3D 子模块的本地文件体积初步控制在 3 MB 内；分别记录原始字节与实际传输字节，不混用 gzip 估算和本地 HTTP 实测。
- 手机设备像素比初始上限 1.5，桌面初始上限 2；按实际画质和性能调整。
- 同时只激活一个渲染器；减少多重实时阴影、透明叠层和后处理。
- 连续运行 5 分钟观察帧率和资源；多次重置/挂载后的资源使用不应呈持续累积趋势。
- 页面隐藏或场景离屏时，不持续推进工艺时间或高频渲染。

如果不达标，优先减少像素比、阴影、透明层和绘制次数，再降低几何细节；不要先牺牲原理可读性。

## 11. 风险、估算与阶段检查点

| 风险 | 应对 |
|---|---|
| 代码模型过于简陋，无法对应照片 | 先评审静态轮廓；关键比例、开口、位置优先于装饰细节 |
| 机器会动但观众不知道发生什么 | 每个阶段强制检查输入、动作、物料变化、输出四项 |
| 不可见结构被当作真实复刻 | 在数据和界面同时记录依据；不确定的机构不用精细模型伪装确定性 |
| 暂停或跳转后状态错乱 | 确定性求值与边界测试，不用多个互不协调的动画计时器 |
| 手机卡顿或发热 | 懒加载、一个画布、离屏暂停、像素比和阴影预算 |
| 构建覆盖原站点 | 独立输出子目录、构建保护测试、原站点全量回归 |

| 新方案使范围不断扩大 | 每阶段设验收点；先单机样板，后共享设备，再九条路线 |

粗略工作量以一名熟悉 three.js 的开发者、简化模型、少量修改为假设：首个样板约 3～7 人日；纳入完整回归、文档和较多视觉打磨可按 5～10 人日预留。模型精度、资料核实和交互反复会明显改变工作量，因此不是固定报价或交付期限。

全量设备和九条路线暂按数十人日量级认识，不在未完成样板前给出精确排期。实施后分别记录内容整理、建模、动画、交互和验证耗时，再据实估算后续。

4. **浏览器与回归通过：** 确认可交付。
